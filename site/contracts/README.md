# Payment data contract

[`payments.odcs.yaml`](payments.odcs.yaml) defines normalized payment batches
for the investigation desk. Contract version 1.0.0 uses ODCS v3.2.0.
The owner is ReguiguiMohamed. [Read the rendered contract](https://reguiguimohamed.github.io/amastan-fraud-shield/contracts/payments.html).

## Boundary

The contract starts after CSV normalization. Raw CSV requires `transaction_id`,
`user_id`, `recipient_id`, `amount_tnd`, `timestamp`, `governorate` and
`payment_method`. `device_id`, `reported_scam` and `expected_fraud` are optional
input columns. Every normalized record contains all ten fields.

Identifiers keep leading zeros and amounts represent whole Tunisian millimes.
The importer trims identifiers, matches governorates case-insensitively,
lowercases payment methods and converts timestamps to UTC milliseconds.
Missing devices become empty strings, missing scam reports become false,
and missing evaluation labels become null. The YAML owns field constraints,
accepted values and batch limits.

The contract covers imported payment records. Hosted API alerts, analyst
decisions and workspace envelopes have separate validation. Historical batches
have no freshness or arrival-order promise. Passing these checks establishes
data conformance, not detection accuracy or payment legitimacy.

## Local checks

[Data Contract CLI](https://github.com/datacontract/datacontract-cli) provides
the contract linting, data tests, compatibility checks and native exports used
here. It is an open-source project under the
[MIT license](https://github.com/datacontract/datacontract-cli/blob/main/LICENSE).
Its [documentation](https://cli.datacontract.com/) covers the commands and
supported data sources.

The pinned CLI version and DuckDB extra live in
[`requirements-contract.txt`](../../requirements-contract.txt), separate from
the application runtime. No paid account, cloud database or credentials are needed.

From the repository root, install the requirements in a disposable Python 3.11
environment, then run these commands with that environment active:

```text
pip install -r requirements-contract.txt
python scripts/generate_payment_contract.py --check
node scripts/generate_contract_fixtures.mjs
datacontract lint site/contracts/payments.odcs.yaml
datacontract test site/contracts/payments.odcs.yaml
python scripts/check_payment_contract.py
```

On Windows set `$env:PYTHONUTF8='1'` before calling the CLI. Its console output
includes Unicode characters.

For your own batch, open **Field notes** in the desk and choose **Export payment
records for CLI**. Set `PAYMENTS_FILE` to the downloaded JSON's absolute path
before running `datacontract test`. PowerShell uses
`$env:PAYMENTS_FILE='C:/path/amastan-payments.json'`. Bash uses
`export PAYMENTS_FILE=/path/amastan-payments.json`.
The default file contains synthetic payments generated by the command above.
Workspace and case JSON exports wrap their records in other structures and
cannot be passed directly to this contract.

## Generated files

Run `python scripts/generate_payment_contract.py` after editing the YAML.

| File | Use |
| --- | --- |
| `payment-contract.js` | Browser import bounds, identifiers, enums and decimal precision |
| `payments.schema.json` | Native CLI export for individual records |
| `payments.html` | Native CLI documentation export |

The browser performs raw-input validation and normalization. SQL checks in
the CLI enforce batch size, transaction uniqueness, whole-millime
precision and real calendar dates. Record JSON Schema alone cannot check
batch-wide uniqueness, row count or these SQL rules.

CI checks generated files against the YAML. Only the native HTML footer's
export timestamp is ignored during comparison. It tests six scenario batches
and a boundary batch, then verifies fifteen deliberate violations fail the
intended checks. Reports remain available as Actions artifacts. Breaking
changes against the base revision fail `datacontract breaking`. Changes that
intentionally break consumers need a separate versioned contract and migration.

The checks are local and use synthetic fixtures. They never query Neon or send
analyst imports to a service.
